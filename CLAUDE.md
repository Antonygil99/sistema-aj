# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Sistema AJ is an insurance CRM (Next.js 16 App Router, React 19, TypeScript, Prisma 7 + PostgreSQL, Better Auth with Google OAuth, Zod 4, Cloudflare R2 via the S3 SDK). The UI, README, docs, API error messages and test names are in **Spanish**; keep new user-facing text and docs in Spanish. Development is on Windows (PowerShell). Node >= 22.12.

## Commands

```powershell
npm run dev              # next dev on http://localhost:3000
npm run lint             # eslint (next core-web-vitals + typescript)
npm run typecheck        # prisma generate && next typegen && tsc --noEmit
npm test                 # tsx --test tests/*.test.ts && node --test tests/*.test.mjs
npm run check            # db:validate + lint + typecheck + test + build (full gate)
npm run theme            # regenerate theme.css after adding colors to workspace.css / help.css
npm run icons            # regenerate src/components/icons.tsx after importing a new icon
npx tsx --test tests/access-policy.test.ts           # single test file
npx tsx --test --test-name-pattern="WhatsApp" tests/architecture.test.ts   # single test
```

Database: `npm run db:up` / `db:down` (Docker Postgres from compose.yaml), `db:migrate` (dev migrations), `db:deploy` (prod), `db:seed` (idempotent fictitious data), `db:studio`. `npm run db:verify-deploy` (scripts/migrate-deploy.mjs) is the explicit hosted-DB deploy: it refuses DBs with foreign tables and no Prisma history, applies pending migrations, verifies app tables, and seeds initial access grants from `AJ_SUPERADMIN_EMAIL` / `AJ_ADMIN_EMAILS`. Never use `prisma db push` as a deploy strategy.

The Prisma client is generated into `src/generated/prisma` (git-ignored, lint-ignored) and imported as `@/generated/prisma/client`; run `npm run db:generate` after schema changes.

## Architecture

**CRM tables (generic resource layer).** Nine modules (`prospectos, clientes, polizas, cotizaciones, pagos, renovaciones, siniestros, documentos, actividades`); each has a strict Zod `createSchema` in `src/modules/<slug>/schema.ts`. The eight non-document modules are driven by one layer: `src/modules/resources/config.ts` (pure: fields, columns, statuses, labels, form↔API conversion, shared with the browser), `rules.ts` (pure, tested in `tests/resources.test.ts`: list filters incl. nested search, full-form update parsing with `expectedUpdatedAt` and nullable clearing) and `server.ts` (Prisma delegates, includes, ordering). Routes: `/api/crm/[module]` (GET list with `q`/`status`/`archived`, POST create ADMIN), `/api/crm/[module]/[id]` (GET, PATCH ADMIN with optimistic concurrency → 409 `RECORD_CHANGED`, DELETE SUPERADMIN), `/api/crm/[module]/[id]/archive` (POST `{archived}` ADMIN). Adding a field means touching its `schema.ts` and `config.ts` (plus `nullable` if optional). UI: `ResourcePage` (server) → `ResourceManager` (client). Amounts are positive decimal strings (`Decimal(12,2)`), dates ISO 8601 sent as UTC midnight, IDs are CUIDs.

**Archive vs delete.** Every CRM record has `archivedAt`; lists hide archived rows unless `archived=1`. Archiving/restoring is ADMIN. Permanent DELETE is SUPERADMIN-only and only succeeds without dependents (FK `Restrict` → 409 `HAS_RELATIONS`); deleting a client also removes its empty default folders. Documents: archive ADMIN, delete SUPERADMIN (row first, then the R2 object). Folders: delete only when empty (ADMIN).

**Events and notifications.** Mutating routes call `recordEvent()` (`src/modules/events.ts`, best effort, never fails the request) into `CrmEvent`, which is both the CRM audit trail and the notification source. `GET /api/notifications?since=` returns teammates' events plus reminders (overdue payments, renewals within 7 days); the workspace polls it every 20 s while visible (no websocket service); the bell opens a panel anchored under it (full width on phones) that respects the user's notification preferences and can be cleared (`clearedAt` / `clearedReminders` in preferences: cleared reminders return when their counts change or the next day, rules pure in `feedView()`), and the poller broadcasts `aj:remote-change` / `aj:documents-changed` window events so open lists refresh themselves. Wording lives in pure `src/modules/notifications.ts`.

**Google Calendar.** `/agenda` and `/api/calendar` are personal to the signed-in user (including USER); no integration token access. Calendar consent is requested separately via Better Auth account linking, Google only and same email, with `calendar.events.owned` and offline access. Tokens remain encrypted in `AuthAccount`; only server-side `getAccessToken` is used. `CalendarConnection` stores enabled state and a one-time connection intent; `CalendarMeeting` stores events owned by that user. Creation reserves a deterministic Google event ID for retries; cancellation is retryable. Agenda shows only CRM-created meetings, can prefill the user's assigned pending activities, and refreshes individual events from Google on request. See `docs/google-calendar.md` for configuration, migration and verification limits. Browser-safe calendar types/helpers live in `modules/calendar/types.ts`; strict request validation lives in `schema.ts`.

**Email (Resend).** `src/integrations/resend/client.ts` is a pure REST client (injectable fetch, errors mapped to codes without echoing Resend) wired by `server.ts`; `src/modules/email/` holds pure templates (`templates.ts`, also used by the composer preview; every CRM value escaped), pure rules (`rules.ts`: allowed recipients, agenda reminder times, reminder plan, webhook status progression, team recipients), Svix verification (`webhook.ts`) and the server-only orchestration (`server.ts`), tested in `tests/email.test.ts`. Every email is an `EmailMessage` row (`dedupeKey` unique, `resendId`, status) — the per-client history and the handle to cancel scheduled reminders. Client emails (documents, welcome) are always sent by a person from `EmailComposer` (`POST /api/emails`, ADMIN, `requestId` idempotent) to the client's email or its `ClientContact` rows only, attaching the client's or the team's general documents read from R2 server-side (≤10, ≤20 MB), from "Name · AJ Consultoría de Seguros" with reply-to the sender. Automatic team notices (new prospect / claim, via `after()` in the generic CRM POST) go to the owner or all admins, never to the actor, and respect `emailProspects` / `emailClaims` preferences; claim notices never carry the description. Agenda reminders (1 day before, 08:00 Mexico City, 10 min before) are scheduled in Resend (`scheduled_at`, 30-day window) by `syncMeetingReminders()` after meeting create/refresh/cancel and by the daily `/api/cron/email` (CRON_SECRET), respecting `emailAgenda`; a change of time or content cancels and recreates them. `/api/emails/webhook` updates delivery status (requires `RESEND_WEBHOOK_SECRET`). The composer and dossier panels (`ClientContacts`, `DossierEmails`) load lazily. Phase 2: `/avisos` ("Avisos a clientes") lists `ClientNotice` rows — renewal 30/20/10 days, receipt 20/10/0 (+3 days grace), weekly open-claim follow-up — generated idempotently by `refreshNotices()` (`notices-server.ts`, rules pure in `notices.ts`, tested in `tests/notices.test.ts`) on every read and in the daily cron; each milestone appears once, stale ones expire. A person sends the suggested email (composer with `noticeId`, the draft comes from `GET /api/emails/options` filling the team's `EmailTemplate` or the default in `template-text.ts`), records another channel or dismisses (undoable). Templates are edited in the Avisos "Plantillas de correo" tab (unknown `{placeholders}` rejected; `[escribe …]` blanks block sending). `sendDailyDigests()` (`digest-server.ts`) mails each admin a morning summary (preference `emailDigest`). See docs/correo-resend.md.

**Products, responsibles and active delivery.** `productos` is a generic resource with `layout: 'cards'` and an `image` field uploaded after save to `/api/products/[id]/image` (private R2 key `aj/products/<uuid>`, never sent to the browser; `imageType` signals an image). Products, policies and activities carry `ownerEmail` (lowercase; `/api/team` lists teammates): Ale owns medical lines, Joel autos. A policy created from a catalog product inherits its responsible. Active delivery (client's "Ruta de implementación AJ"): policy columns `deliveredAt`, five `delivery*` checks and `referralPotential`; rules are pure in `src/modules/polizas/delivery.ts` (stages emitida → entregada → explicada → seguimiento 7 → seguimiento 30 → posible referido, follow-ups at 7/30/90 days; tested in `tests/delivery.test.ts`). `PATCH /api/policies/[id]/delivery` saves with `expectedUpdatedAt` and creates/reschedules `Activity` rows with `kind` `SEGUIMIENTO_7/30/90` assigned to the policy's responsible. The board lives at `/crm/entregas` (`?open=<policyId>`, `?owner=me`); reminders include the viewer's due follow-ups. Medical history is recorded only as existence (no detail) — a client decision for the diagnosis stage.

**Prospect pipeline (Ruta AJ etapas 1–4).** `ProspectStatus` is CURIOSO → DIAGNOSTICADO → COMPARATIVO → EMISION, plus CLIENTE (only via conversion, linked by `convertedClientId`) and PERDIDO. The five diagnostic questions live on `Prospect` (`diag*`); `diagMedicalHistory` stores only SI/NO/NO_SABE (never details) and `redact()` strips it for USER accounts. Rules are pure in `src/modules/prospectos/pipeline.ts` (tested in `tests/pipeline.test.ts`): answering all five moves CURIOSO to DIAGNOSTICADO via `applyRules()` on create/update; setting CLIENTE without conversion → 422 `USE_CONVERSION`. Prospects default to the "Embudo" board view (`board` in config; the page loads 100 rows). Conversion: `/crm/clientes/nuevo?prospect=<id>` prefills the dossier wizard; `POST /api/dossiers` with `prospectId` creates the client and marks the prospect CLIENTE in the same transaction (guarded, 409 `ALREADY_CONVERTED`). `referredByClientId` records who recommended a prospect.

**Global search.** `GET /api/search?q=` (≥2 chars) queries every CRM table via `searchResource()` plus documents, folders and — SUPERADMIN only — access grants; result shaping, destinations and grouping are pure in `src/modules/search.ts` (tested in `tests/search.test.ts`). The topbar `CommandSearch` palette (⌘K / Ctrl+K) shows quick actions and recent picks when empty. Results deep-link: clients → dossier, tables → `/crm/<slug>?q=…&open=<id>` (the card opens on load), folders → `/crm/documentos?folder=<id>`, files download.

**UI kit (`src/components/ui/`).** Providers mounted in `WorkspaceShell`: `ToastProvider` (`useToast`; also listens to `aj:security` from `apiFetch` on 401/403/INVALID_ORIGIN and to online/offline), `ConfirmProvider` (`await useConfirm()(…)`), `UploadProvider` (`useUploads().enqueue` — Drive-style background queue via XHR with progress, 2 concurrent, survives client navigation). `Modal` is a dialog on desktop that grows from its trigger (GSAP shared-element) and a swipe-to-close bottom sheet ≤760 px; it portals into `#workspace-portal` so `.workspace`-scoped CSS applies. Use `apiFetch` (`client-api.ts`) for browser calls: it maps error codes to Spanish messages. Gestures use `useDrag` (pointer events with axis lock). `Avatar` (`ui/avatar.tsx`) shows the Google profile photo (`session.user.image`, exposed by `currentUser()`) with an initials fallback; it is shared by the sidebar `AccountMenu` (account row that opens a fixed-position menu beside the sidebar with the role, Usuarios y accesos and Cerrar sesión), the mobile "Más" sheet and the users list. `EmptyState` renders unDraw SVGs from `public/illustrations/` (recolored `#6f9a82`). Motion: `motion.ts` (GSAP, transform/opacity only, reduced-motion fallback). Icons come from `@/components/icons`, generated by `npm run icons` (`scripts/build-icons.mjs`) as inline SVG for only the Iconsax icons the code imports (Linear, plus Bold in files that pass `variant`); `iconsax-reactjs` is a devDependency and `tests/icons.test.mjs` fails on a direct import or a stale file. Every workspace route has a `loading.tsx` rendering `PageSkeleton` (`ui/page-skeleton.tsx`: dashboard, module or detail shape) so navigation shows the next screen instantly. Mobile (≤760 px) uses `MobileNav` (bottom tab bar + "Más" sheet) instead of the sidebar. Design rules from the UI/UX audit (UI/UX Pro Max): text is never below 12px (mobile body 15px, inputs 16px to avoid iOS zoom); text colors must reach 4.5:1 on the lightest pastel background (gray text ≈ #5d6a63 or darker); tap targets are 44px on ≤760px and ≥24px on desktop; field focus uses a 2px #3f6b54 outline; form errors render under their field (aria-invalid + aria-describedby) with focus moved to the first one; closing a dirty form asks before discarding; destructive confirmations focus the safe button. Watch for unscoped element rules in `globals.css` (`header`, `footer`, `aside`, `.nav-label`) leaking into new components.

**Light/dark theme.** Workspace stylesheets never contain raw hex colors: `scripts/theme-tokens.mjs` (`npm run theme`) rewrites every hex in `(workspace)/workspace.css` and `help.css` to a token `var(--c-<hex>)` and generates `(workspace)/theme.css` with the light value and a derived dark value (OKLab: lightness inverted, hue kept, grays tinted green, shadows kept dark; page backgrounds hand-picked; the funnel ramp has its own validated dark steps as `--funnel-1…5`). Write colors as plain hex and run `npm run theme`; `tests/theme.test.mjs` fails if the generated files are stale or a raw hex remains (use `rgb()` only for colors that must not change with the theme, like the theme previews). A fourth theme, `gradient` (base `#FC66FF`), derives its tokens with `gradientColor()` (plum surfaces, light text that stays readable over the canvas, workspace greens moved to the base color; positive status pills keep their green) and paints the main panel with a fixed grainy gradient (`--canvas-*` + an SVG noise overlay, handwritten in workspace.css with `rgb()`); it forces the icon-only sidebar. `TooltipLayer` (`ui/tooltip-layer.tsx`) shows one fixed tooltip for elements with `data-tooltip` (sidebar items when compact, or `data-tooltip-always`); the accessible name stays in `aria-label`. The theme (`light | dark | system | gradient`) is a user preference: the shell renders `data-theme` on `.workspace` (no flash) and mirrors it on `<html>` for things mounted in `<body>` (driver.js). `body` keeps globals.css colors, so the workspace sets its own text color in dark mode. Popovers that must float above the page (account menu, notification panel) portal into `#workspace-portal`, because the sticky sidebar is its own stacking context.

**Preferences, Help Center and guided tours.** `UserPreference` (keyed by lowercase email, JSON `data`) stores each user's view choices and tour state; rules are pure in `src/modules/preferences.ts` (tested in `tests/preferences.test.ts`; unknown keys or values are rejected by `PATCH /api/preferences` with the strict zod schema in `preferences-schema.ts` and dropped on read). The workspace layout loads them once (`getPreferences`, server-only) into `PreferencesProvider` (`usePreferences().update` saves in the background with `keepalive`). Remembered views: clients dossiers/list (`?view=` wins; `ClientViewSwitch` shows the same "Expedientes | Lista" switch in both toolbars — the list gets it through `ResourcePage`/`ResourceManager` `toolbarStart`), the prospect board/list (`ResourcePage` loads 100 rows only for the board) and documents grid/list. The account menu (and the mobile "Más" sheet) opens the Help Center (`help-center.tsx`) and Preferencias (`settings-dialog.tsx`: theme, notification types, the assistants' Claude model — stored only, no AI runs yet —, automatic tours, reset remembered views), has a quick dark-mode switch and shows Reportes disabled ("Próximamente"); both panels live in `AccountPanelsProvider` (`ui/account-panels.tsx`). Tours run on driver.js 1.8.0 through `TourProvider` (`ui/tours.tsx`), which imports `ui/tour-engine.ts` (driver.js + its CSS) only when a tour starts; the Help Center and Preferencias are `next/dynamic` and download the first time they open; their content is pure in `src/modules/help/tours.ts` (tested in `tests/tours.test.ts`): each step lists CSS targets and the first visible one is highlighted, missing ones are skipped. With "Recorridos automáticos" on, each screen's tour runs once and is marked seen. driver.js mounts its popover in `<body>`, so its theme in `(workspace)/help.css` is scoped with `.aj-tour` and resets the global `header`/`footer` rules. When a screen changes, update its tour selectors.

**Client dossiers.** `/crm/clientes` renders clients as dossiers (`?view=list` keeps the contact list, and the last choice is remembered); each dossier card is a folder whose front tilts open on hover and further while its page loads (`LinkPending` uses `useLinkStatus`, CSS reacts with `:has()`); `/crm/clientes/nuevo` is a 4-step wizard and `/crm/clientes/[id]` the dossier detail. `POST /api/dossiers` creates client + default document folders + optional policy with its payment schedule in one transaction; `POST /api/dossiers/[id]/policies` adds a policy. Premium/schedule/coverage rules are pure in `src/modules/clientes/dossier-policy.ts` (tested in `tests/dossiers.test.ts`): receipts must sum exactly to the premium in cents, coverage state comes from policy dates, never from payments.

**Auth and authorization.** `src/lib/auth.ts` builds Better Auth lazily (`getAuth()` returns null when env is incomplete → APIs answer 503 `AUTH_NOT_CONFIGURED`). Better Auth models are renamed (`authUser`, `authSession`, ...). Access is governed by `AccessGrant` rows (roles `USER < ADMIN < SUPERADMIN`) with pure logic in `src/lib/access-policy.ts` (unit tested; SUPERADMIN is only honored for the email in `AJ_SUPERADMIN_EMAIL`). Sign-up and session creation reject non-granted or unverified Google accounts.
- API routes call `authenticate(request, minimumRole)` (returns `{ denied }` or `{ actor }` for event attribution) or the thin `authorize()` wrapper from `src/lib/api.ts`. Both accept `Authorization: Bearer $AJ_API_TOKEN` (server-to-server, acts as "Integración interna", never SUPERADMIN) or a session cookie, in which case non-GET requests must have `Origin` equal to `BETTER_AUTH_URL`.
- Errors go through `apiError()`: Zod → 400, domain errors carrying `code` + `status` (`ResourceError`, `FileError`, …) pass through, `P2002` → 409, `P2003` → 422, everything else → 503 without leaking details.
- Pages use `requireUser(minimum)` from `src/lib/session.ts`; the `(workspace)` route group layout enforces login for all CRM screens. `/usuarios` + `/api/users` are SUPERADMIN-only access management, with audited changes.

**Documents (R2).** Files are uploaded to a private R2 bucket via `POST /api/documents` (multipart, ADMIN) and downloaded via `/api/documents/[id]/download` (short-lived presigned URL). The generic CRM POST deliberately rejects `documentos` (`USE_DOCUMENT_UPLOAD`). Logic is split for testability: `file-policy.ts` (size/type validation, bounded form parsing) and `file-operations.ts` (pure orchestration against injected `DocumentRepository` / `FileStorage` interfaces) contain no `server-only` imports so `tests/documents.test.ts` can exercise them with in-memory fakes; `files.ts` and `src/integrations/r2/server.ts` wire in Prisma and R2. Never return bucket keys or permanent URLs to the browser. Documents live in a `DocumentFolder` tree scoped to the team library (`clientId` null) or a client dossier; scope checks are in `src/modules/documentos/folders.ts`. Folders have a `color` (palette and the stable default tone are pure in `folder-view.ts`, tested in `tests/folders.test.ts`) and `archivedAt` (archive/restore at `/api/folders/[id]/archive`, archived list at `GET /api/folders`; listings and search skip archived folders, whose contents stay untouched). The library card reuses the client dossier's three-layer folder (`.dossier-card.doc-folder` + `folder-color-*`); ⋯ or right-click opens one context menu (portaled, keyboard navigable) for a folder or for the empty area. React listens on `document` in the App Router, so an outside-click listener on `document` must check `contains()` instead of relying on `stopPropagation()`. The case-insensitive sibling-name index `DocumentFolder_sibling_name` exists only in migration SQL (Prisma can't model expression indexes): strip any `DROP INDEX` for it from future generated migrations.

**Policy upkeep.** `scripts/policy-maintenance.mjs` (dry-run by default, `--apply` to write, same advisory lock as the importers): `--renewals[=60]` creates a PENDING renewal for each active policy ending within N days (Mexico City) without an open renewal, with deterministic ids so reruns never duplicate; `--clean-details` clears placeholder values (S/N, N/E, SINDATO…) from plates/vehicle/use/coverage, keeping the original in `Policy.sourceData`; `--assign-owners --autos=<email> --medicos=<email>` fills missing responsibles on policies and catalog products by line (autos → AUTO; medical → MEDICAL plus "Accidentes y enfermedades"), never overwriting one, with the emails passed on the command line so they are not stored in the public repo. Policies imported from the August 2026 control file are documented in docs/importacion-control-polizas.md (21 policy numbers were held for review).

**Migrations vs. deploy.** The Vercel build only runs `prisma generate && next build`. Apply new migrations to production with `npm run db:verify-deploy` *before* pushing code that depends on them.

**Performance.** Prisma Postgres sleeps when idle (first query ≈ 4.7 s); `.github/workflows/keep-warm.yml` pings `/api/health?db=1` every 5 minutes from 06:00 to 22:59 Mexico City. Keep zod out of the browser: modules that client components import stay zod-free and their request schemas live apart (`preferences-schema.ts`, `polizas/delivery-schema.ts`, `documentos/file-types.ts` for upload limits); only the dossier wizard ships zod, on its own routes. Measured from Vercel (iad1) a warm query takes ~10 ms.

**Server-only boundary.** Modules touching secrets, Prisma or auth import `'server-only'`. Code that tests import must stay free of it (tests run under plain `tsx`/`node --test`, not Next), so put testable logic in pure files and keep wiring in thin server-only wrappers. `getDb()` (`src/lib/db.ts`) is a global singleton using the `@prisma/adapter-pg` driver adapter and accepts the legacy `DATA_URL` alongside `DATABASE_URL`. Migration URL resolution (`DIRECT_URL`, or rewriting the Prisma Postgres `pooled.db.prisma.io` host) lives in `scripts/migration-url.mjs` and is shared by `prisma.config.ts` and the deploy script.

**Assistants (Claude API, superadmin only).** `/asistentes` hosts the eight single-purpose Ruta AJ assistants (`src/agents/catalog.ts`, pure: id, name, tools, suggestions); the page (`requireUser('SUPERADMIN')`), `/api/assistant/*`, `/api/agents`, the sidebar/mobile links, the dashboard assistants panel, the Preferencias model section and the tour are all superadmin-only. Each turn (`POST /api/assistant/chat`, NDJSON stream of `step`/`text`/`proposal`/`notice`/`done`/`error`) runs `runAssistantTurn()` (`src/agents/server.ts`): the preferred model among light ones only (`assistantModels`, each with its provider: `claude-haiku-5-5` default, `claude-sonnet-5-5`, `gpt-6-luna`, `gpt-6.1-sol`), low reasoning effort (medium with "Pensar a fondo"), stable per-assistant system prompts (`prompts.ts`) and the date/user/role in a separate message. `runAgentLoop()` (`loop.ts`, pure, tested in `tests/agents.test.ts`) is provider-independent: a `ModelDriver` per provider keeps the conversation in its own format — `drivers/anthropic.ts` (Messages API streaming, adaptive thinking, cached prompt, eager tool streaming, refusal fallback on Sonnet only, pause_turn, JSON-only retries) and `drivers/openai.ts` (Responses API streaming, `store: false` + `include: ['reasoning.encrypted_content']`, output items replayed with `toResponseInputItems` before `function_call_output`). The loop validates every tool input with zod, returns all results together and stops on refusal or truncated tool input. Tools live in `tools.ts` (server-only): read tools return compact JSON with internal links and never medical history values or claim descriptions; write tools (`crear_actividad`, `registrar_prospecto`, `mover_prospecto`, `resolver_aviso`, `preparar_correo`) only produce proposals that the user confirms, executed by `POST /api/assistant/actions` (ADMIN, re-validated); `preparar_correo` opens `EmailComposer` with a `draft`. Write tools need ADMIN or above (always true for the superadmin). Agents never get Prisma or shell access; tool data and WhatsApp text are untrusted. The chat UI is `ui/thinking-prompt-input.tsx` (ThinkingPromptInput ported to workspace CSS and iconsax). Turns are logged in `AgentRun`; requires `ANTHROPIC_API_KEY` and/or `OPENAI_API_KEY` (503 `AI_NOT_CONFIGURED` without both; `AI_ANTHROPIC_NOT_CONFIGURED` / `AI_OPENAI_NOT_CONFIGURED` when the chosen model's key is missing). See docs/asistentes.md. Do not invent "Método AJ" business rules; they await business documentation.

**WhatsApp (scaffolding).** `/api/whatsapp/webhook` verifies `x-hub-signature-256` HMAC over the raw body and persists `WebhookEvent` rows deduplicated by `payloadHash`; no consumer/worker exists yet (`processedAt` stays null); the first-contact assistant can read those messages as untrusted data. Outbound WhatsApp requires human approval.

**Dashboard metrics.** The home page (`src/app/(workspace)/page.tsx` loads data, `src/components/dashboard-overview.tsx` renders) shows real numbers from `dashboardMetrics()` (`src/modules/metrics/server.ts`, ~23 parallel counts): active prospects and the Ruta AJ funnel, active policies and premium, policies issued this month, renewals within 30 days, delivery completion and late follow-ups, overdue receipts, open claims, referrals and quotes. The owner chips show each teammate's Avatar (Google photo after their first sign-in, initials and the email's user part before). `?owner=me|all|<email>` scopes them to one responsible (policies/prospects/activities by `ownerEmail`; payments, renewals and claims through their policy; quotes through their prospect). Months are Mexico City calendar months (fixed UTC-6) and deltas compare with the previous month; that logic is pure in `src/modules/metrics/period.ts` (tested in `tests/metrics.test.ts`). Response times and content cases are not measured yet (they need WhatsApp and a content log).
